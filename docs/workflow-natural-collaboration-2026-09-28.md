# Workflow v3：自然交流、按需协助和完整交付

日期：2026-09-28。本文描述本次实现的目标与代码行为；实际验证结果单独记录在末尾。先前 PR #54 的 v2 验收和 PR #56 的原生菜单修复不自动构成本次 v3 验收证据。

## 用户可见行为

新建 workflow 任务使用 `task.promptVersion = 3`。讨论参与者按序回应对方的实际意见，详细分析写入材料文件，原生聊天只给简短结论、分歧及材料位置。不会要求参与者在聊天正文里反复粘贴状态 JSON、任务书和完整报告。

飞书不逐条转发参与者的中间输出，默认 Web 消息历史也不展示这些内部轮次。程序保留原始会话、参与者输出和调度证据。常规生命周期不再调用 pi 生成进度通知，仅发送必要的开始通知、真实阻塞和最终交付；权限菜单沿用专用自动审批及必要的人工卡片。

最终交付是简短摘要卡和完整 `report.md` 附件。用户明确要求的讨论文档会把实际内容及 hash 收录在报告附录，冻结时核对文件，用户可直接从飞书附件阅读设计文档。摘要包含报告结论、产物位置、验证来源；开发任务还展示实际采集的 Git 分支、提交和可核验的对应 PR。没有取得 Git 或 PR 证据时明确说明未确认。摘要及附件交付不等于用户验收，不自动完成任务或清理执行器。

用户可以直接在飞书问“这个任务进展怎样”“Claude 和 Codex 现在讨论到哪里”。pi 先查任务，再用 `task_progress` 读取绑定原生会话及当前状态，自然总结实际进展、分歧和阻塞。读取失败会返回明确错误，不能把空闲、缺少输出或一轮回复结束解释为任务完成。

## Jev 和 pi 的职责

入口仍遵循“规则 → Jev → LLM”。身份、群绑定、回执和候选合法性由程序保证；私聊 intent/project 分类仍由独立的 `jev.ingress_enabled` 控制，默认关闭。配置 key 不会自动开启私聊分类。

v3 的任务内选择分为两层：

| 情况 | 实际行为 |
| --- | --- |
| Jev 判断当前实际模板已经足够 | 直接实例化该模板，无需 pi 规划 |
| Jev 判断需要额外分解或协调约束 | pi 通过 `orchestration_plan` 细化计划，之后仍受计划校验约束 |
| 当前只有规则确定的合法动作 | 程序按规则推进并记录理由 |
| Jev 能高置信度选择合法动作 | 采用该候选，继续既有派发链 |
| Jev 明确请求协助 | pi 只可用 `orchestration_decide` 在原合法业务候选中选择 |
| Jev 第一次低置信度 | 再评估一次“请求 pi / 等待证据”；低置信度本身不直接触发 pi |
| 协助评估选择等待或仍然不确定 | 持久保存等待状态；相同证据下不再调用模型或消耗重试，材料或用户修订变化后重新判断 |
| Jev 网络、服务或协议失败 | 使用显式故障恢复策略，可调用受限 pi；日志标明 `requestedBy = recovery` 和具体原因 |

任务内 Jev 判断会收到用户要求、当前合法候选、状态证据，以及最近参与者对话和有限材料片段；材料可能含用户项目内容。这与默认关闭的私聊分类是不同的数据路径，不会因此扫描或上传整个仓库。

pi 仍处理用户入口、主动进度查询和必要的规划/选择协助。停止后台进度通知不等于从产品中移除 pi。原生权限菜单的 `approval_decide` 属于此前已交付的独立审批链，本次不把它替换成任务消息或任意终端输入。

每次选择保留规则结果、Jev 分布、请求协助的原因、最终策略来源和原候选。派发继续落入 `OrchestrationEvent.decision`、`dispatches`、`tasks().send` 和回执对账，不增加第二套执行队列。

## 独立文件回执与恢复

看板位于 `stateDir/tasks/<id>/board/`，作为附加目录提供给参与者。看板、材料和机器回执不会为此写入用户仓库，也不修改 `.git/info/exclude`。

每次派发有独立交接目录，包含：

- `brief.md`：本轮用户要求、角色安排、文件范围、前序材料位置及验证约束。
- `request.json`：程序生成的本轮协议及归属字段。
- `notes.md`：参与者的完整分析、回应和依据。
- `result.json`：参与者填写的独立状态回执。
- `report.md`：仅报告节点生成的完整分章节报告。

回执保留 `nodeId`、`operationId`、`inputRevision`，自然语言交接还必须指向本轮 `notes.md`。程序核对投递回执、输出序号、材料归属、文件类型和内容，再推进节点。缺失、畸形、旧轮次或越界的回执不会被自然语言“已完成”替代。材料会保存为任务内可回读的证据，供后续参与者和 Jev 使用。

用户修订、计划版本、阶段、代码变化和任务操作继续并入既有 revision 与 superseded 机制。重启后复用已冻结派发和回执；投递结果未知时不自动重发。没有新增轮数上限：未决问题持续没有进展时请用户裁决，不按固定轮数强制综合或结束。

## 讨论文档的授权

“只讨论、不开发”不再一概等同于“不能交付用户已经要求的文档”。例如用户明确要求“讨论设计并保存到 `docs/DESIGN.md`，不要开发业务代码”，规划会记录 `documentDelivery`，保留完整用户要求，由 Jev 核对动作和路径，再安排限定文档节点。

文档节点只允许任务主目录内明确列出的 `.md`、`.txt`、`.rst`、`.adoc` 文件；绝对路径、隐藏路径、路径穿越及符号链接不作为文档写入授权。实际写入前后核查路径和授权文档之外的项目版本，发生越界变化时阻塞处理。定制计划必须为每一个交付路径安排写入节点，缺失分工的计划会被拒绝并要求补齐。文件必须实际存在并有当前版本哈希，之后由未参与该文档写入的参与者复核，才能满足最终报告合同。

任务保存首次文档写入前的源码基线，排除范围仅为已授权文档；每个节点还单独核验自己的写入范围。用户 resume、计划重建及问题关闭都不能把尚未恢复的越界改动纳入新基线。修改文档授权范围前必须先通过旧范围核验，任务目录变化也不能静默重建基线。派发、回执处理和最终交付都要核对该基线；历史任务若已派发文档写入却缺少可恢复的可信基线，会明确阻塞，不能使用当前工作区伪造初始证据。

用户明确要求文档落盘时，不重复索取同一授权；“只读分析”“不要写文件”等否定和后续修订仍然有效。参与者意见不是用户授权。文档授权不扩展为实现代码、修改配置、安装依赖或提交 Git。Jev 无法确认文档范围时保留现场，不凭文件后缀推断授权。

项目 `verify` 的边界保持不变：只有本地配置的命令可以由 myrix 执行，使用任务实际目录和有限超时，并记录 stdout/stderr 与退出事实。用户明确禁止验证时保留原文约束和独立只读复核，报告标注未运行。固定 cwd 不是 OS 沙箱，文档写入检查也不能被表述成原生执行器的文件系统沙箱。

## 报告交付及主动查询

报告附件上传、文件消息发送和摘要卡发送分别持久化状态。已确认上传后若文件消息明确未发送，只恢复原文件消息；文件或卡片结果未知时不重复发送。完整报告（含全部文档附录）按 UTF-8 总字节数在冻结前检查 10 MiB 附件上限，超限会返回报告节点修正，不会冻结一个必然发送失败的附件。只有完整交付合同满足才确认交付。旧版本“正文加卡片”的回执继续按原方式恢复。

本机历史页的报告摘要提供“下载完整报告 report.md”。下载请求只接受 owner 和摘要消息身份；服务端验证允许名单、任务归属、会话归属、冻结报告标识及哈希，然后返回冻结内容。接口不接受任意文件路径。它依旧是本机单用户历史页面，不是远程文件托管服务。

`task_progress` 只读取当前 owner 可访问的任务；任务群只能查绑定任务。参与者来自任务内绑定，不能指定任意 session 或 transcript 路径。原生读取通过既有解析器和初始 receipt 核验 session/cwd，仅返回该输入之后的有效用户、助手和工具摘要，不读取推理块或其他任务的先前对话。

查询返回最近的有限对话片段，较早记录可按参与者独立分页；单条和总文本上限会明确截断。查询不改变调度器的 transcript cursor，不派发新输入。当前原生状态、工作流问题、产物、验证来源、报告和完成时间分别返回，pi 不得把参与者自述升级为程序已验证或用户已验收。

PR #57 首轮自动审查提出的三项问题已补专项回归：等待证据不消耗重试且跨重启保持、定制图必须覆盖全部文档路径、附件总大小在冻结前检查。主动查询还覆盖 Claude 单条原生记录同时包含正文和工具时的 40 条消息上限，分页不丢失或重复。

本轮专项 38/38 通过，类型、lint、行数和构建通过。冻结委派恢复测试覆盖任务总范围合法但当前节点范围已变化时拒绝发送；报告通知恢复测试确认发现源码污染后只发一次阻塞通知。旧 v2 和无文档能力的开发任务不因缺少文档基线受到影响。
