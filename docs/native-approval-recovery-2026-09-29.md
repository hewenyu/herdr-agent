# 原生菜单确认与默认文件日志修复

## 真实现场与原因

2026-09-29 的 v0.3.20 任务在首次目录信任界面停止，两位参与者均未确认收到初始任务。
本轮只读检查了任务记录、自动审批持久快照、入口 pi checkpoint 和当前原生状态，没有向用户现场发送按键或重启服务。

- Codex 已高亮 `1. Trust and continue`，页脚为 `enter continue · esc back`。Jev 低置信度后，pi 选择 `key:1`；程序按 literal key 发送数字 `1`，菜单未变化，记录 `approval_unconfirmed`。
- Claude 实际高亮 `No, exit`，另一项为 `Yes, I trust this folder`。pi 错误声称当前已高亮 Yes 并选择 Enter。之后执行器消失，与确认退出吻合，程序记录 `input_unconfirmed`。
- Jev 两次置信度为 0.53、0.39，均低于 0.8 门槛，已正确进入 pi 后备选择。旧日志的 `source: pi` 和 `confidence` 混用不同来源，容易误读。
- 任务已经 `bypass: true`，Claude 屏幕也显示 `--dangerously-skip-permissions`。常规工具审批的 Bypass 不能保证消除启动目录信任菜单。
- 入口 pi 显式传入 `orchestration.mode: model`，绕过了 workflow 默认值。历史测试任务中的“普通审批等群里用户”等约束被带入新任务 requirements，但本次用户原文没有这些限制。

## 行为修改

Jev/pi 从真实菜单选项中选择目标，程序从游标与界面按键提示推导一次操作。编号不再被当作热键；需要移动时先导航并回读，目标已高亮时才确认。选项身份关联菜单内容和顺序，不能复用到不同菜单。既有手动审批和执行结果未知时的停止重试规则保留。缺少可验证控件信息的界面仍需用户处理，不能把任意未来界面识别成功作为保证。

有服务端用户原文时，自动审批只读取该原文和任务范围内修订作为授权输入，不把 pi 整理的 requirements 作为额外审批政策。缺失原文的历史任务保留明确标记的兼容来源。主入口及摘要提示词明确约束所属任务，旧任务限制和历史助手承诺不能自动套用到新任务。

自动调度模式由服务配置决定：AI 和 Jev 已配置时，新任务中的旧 `model` 参数归一为 `workflow`，启用 v3 看板、自然协作和安静通知。任务身份仍根据原创建输入计算，已有任务的幂等回读先于归一化，不能借升级迁移旧任务或重复建任务。明确的 manual 和旧 round_robin 控制保持原语义。

`myrix`、`serve` 和 `configure` 取得状态锁后默认启用文件日志，见 [本地服务日志](local-service-logs.md)。诊断文件沿用脱敏和最少字段，不保存凭据、用户全文或原生完整屏幕；详细审批快照仍在本地状态记录。日志故障明确降级到控制台，不影响已经发生的业务效果。

## 验证边界

回归必须覆盖本次 Codex/Claude 菜单的选择、导航、确认与故障回读；同时覆盖旧任务幂等恢复、新建任务入口、默认日志追加/轮转/权限及 CLI 接线。真实 Jev/pi 选择探针使用隔离的合成屏幕，禁止原生写操作和飞书消息。

构建与离线测试不能代替真实原生 CLI 加飞书的完整验收。用户当前失败任务不由这次代码修复自动重放或恢复；已记录 unknown 的按键继续保留待核对状态。
