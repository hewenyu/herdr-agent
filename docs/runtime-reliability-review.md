# 运行可靠性改进与任务群清理诊断

本轮在 `fix/runtime-reliability-and-group-cleanup` 分支实施小步改进，不重写授权、幂等回执或 workflow 架构。原始状态、原始操作回执和模型视图仍相互区分；未知写操作不得盲目重放。

## 现场诊断（只读）

现场进程为 v0.3.25，基于提交 `f63536daf5e20b187ae4f798cb2ea2ce59801516`。2026-10-01 01:00:52 UTC 启动，随后飞书连接就绪并完成 service.ready。SQLite 的 ExperimentalWarning 本身不是启动失败。日志中早于本次 service.started 的飞书错误不应归因于本次启动。

针对“任务完成但群未自动解散”，通过只读 SQLite 查询确认：

- 用户完成操作已有成功处理记录；任务处于 `destroying`，而非仅有报告的 `review`。
- `keepGroup=false`、`closeRequested=true`、`groupDeleted=false`。
- 两名参与者均为 `gone`，各自关闭操作已有 `done` 回执。
- 群内没有未完成的 outbox 记录。
- 尚无删除群的操作回执：不是飞书删群 API 返回失败，而是调用前的本地门禁仍未通过。
- 两条旧入站消息为 `uncertain`，自动恢复已达三次，失败通知已投递。其对应版本化 turn receipt 为 `failed`；检查点仅有只读查询，且没有对应 turnId 的写操作日志。
- 原门禁一律阻止任何 `uncertain` 入站消息，因此即使只读模型失败、通知已送达，也会无限期阻塞已经授权的任务收尾。

本次启动后的另一条查询因模型答复缺少工具事实而失败，最终为 `failed/not_executed`，并不是上述两个旧 `uncertain` 阻塞项。不能把模型生成失败、执行失败、投递失败和清理门禁混为同一问题。

四个实施代理均正式交付、源码恢复并经主代理审查后，以 `DatabaseSync(..., { readOnly: true })`、`query_only=ON` 和仅提供 get/list SELECT 的适配器，对当前真实记录重新进行了最终只读预演：两条阻塞消息均返回 `proven=true, reason=settled`，新的入站/出站消息门禁返回允许收尾；实际任务仍为 `destroying`、`groupDeleted=false`。另外用 SELECT 确认整个群的报告投递记录数和尚未通知的 deliver 意图数均为零，没有调用可能修改记录的报告投递服务。预演证明包含严格 replyId/sessionId 校验的最终补丁能够识别此次阻塞数据，包括通知正文与版本化指纹；这不是部署后的完整生命周期现场验收，更没有执行真实删群。

## 安全约束

清理门禁的收敛必须以持久化事实证明，而非根据消息年龄、失败次数或任务显示“完成”直接忽略未知状态：

1. 只读失败没有副作用，与未知写操作不同；只允许经过精确身份、版本及投递证明的窄范围例外。
2. 原始 `uncertain` 审计不应改写为“操作成功”。允许收尾不意味着模型成功答复，也不意味着用户见过模型未发送的内容。
3. 排队中、处理中、未知写操作、缺失证明、未送达输出仍必须阻塞。
4. 群保留设置、最终原生结果投递、执行资源关闭、收尾通知和 report delivery 等其他门禁保持不变。
5. 本轮不改写现场状态、不重启现场服务、不调用飞书删群 API；新版部署后是否能最终解散，仍需现场确认。

## 改进范围

- Leader 持久记录读取：在恢复与写入关键边界拒绝不支持或缺失的版本，不静默解释未来格式；保留已有身份隔离规则，不将版本检查宣称为完整 schema 验证。
- 任务详情查询：按所请求 section 延迟构建，避免只查参与者却扫描其他 namespace、读取报告。保留分页与授权语义；不声称已消除所有全局扫描。
- 工具事实日志：保留明确允许的有界标量诊断，不放宽凭据/正文过滤，不改变业务工具结果。
- 任务群收尾：消除有充分持久证明的只读失败回合造成的永久等待，不豁免未知副作用。
- 真实崩溃测试：子进程在 intent 已持久化、外部效果完成、成功回执提交三个边界由父进程 SIGKILL；重开真实 SQLite 验证未知效果不重放、已确认结果复用。
- 文档：修正仍把 Jev 描述为 workflow 主调度器的旧设计内容；[中文说明](../README.zh-CN.md)和[英文说明](../README.md)明确已配置验证命令仍会执行参与者可修改的工作区脚本，不等于沙箱或不可变的可信代码。

## 安全审查补充与边界

- 自动审批已有候选集合、任务/执行器/屏幕校验和未知按键效果冻结，但“优先单次、最小权限”仍有模型语义依赖。持久授权、会话级授权和目录信任需要更明确的程序化授权分类；不能将候选 ID 校验等同于已保证单次授权。仅过滤选项标签中的关键词也不完整：原生 y/n 菜单的标签可能只有 Yes/No，授权范围在屏幕上下文中。此项保留为后续设计与兼容性验证，不声称本轮已消除。
- 验证命令来源受项目所有者配置约束，但命令执行的脚本可以被参与者修改。这是当前服务账户执行模型的信任边界，不是模型可任意提供 shell 命令的证据；本轮明确文档边界，不引入未经设计的脚本哈希固定或 OS 沙箱。
- 工具 schema 关键字白名单/编译契约，以及各查询工具输出的统一不可信数据标记，可作为后续增强；本轮不将依赖库的宽松行为本身定性为已发生的权限绕过。
- verify 重启后的 `unknown` 会继续阻塞重叠目录，目前没有独立的安全人工决议出口。这是可恢复性缺口，但禁止旧 PID 重用、禁止未知进程仍运行时自动释放目录的安全约束必须保留；不能直接套用 `failed`、`retry` 或 `abandon` 来解除互斥。本轮没有现场证据表明它造成了此次群清理问题。
- 人工审批卡片有 owner/chat、单次 nonce 和执行现场校验，但没有与自动审批相同的任务生命周期/暂停修订绑定。需要明确“暂停调度”与“所有者显式手动输入”的权限关系，并设计完成/关闭期间的旧卡片失效语义；本轮不以复制自动审批策略的方式悄悄改变手动控制权限。
- 恢复工具结果的十项定向回归发现四条可复现缺口：无法解析的旧写结果、无法解析的旧错误文本、缺少明确 outcome 的错误，以及旧工具不再注册时的明确 unknown，都会错误允许后续新写入。日志代理交付后，主代理已补修，十项回归全部通过：已注册或已移除工具的 unknown 均阻塞写入，明确未执行与确认成功仍允许继续，只读失败不阻塞写入。工具不再注册不能清除未知效果，也不能把未知读写属性当成已确认写入；新增断言同时覆盖这两点。

## 暂不实施

独立 read-model 索引、全面事件溯源、Cordis 化、大规模状态迁移和自动化部署不在本轮范围。它们需要单独的基准、迁移/重建协议和验收证据。离线测试通过不等于飞书、模型服务及 herdr 全链路现场验收通过。
