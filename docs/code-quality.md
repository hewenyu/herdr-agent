# 代码质量与开发约定（Node / TypeScript）

本文描述当前代码的开发约定，不是历史 Go 审计或真实业务验收记录。

## 本轮审查结论

基线：`d3d3950`（PR #66），治理分支：`refactor/code-quality-boundaries`。

项目已有较好的基础：TypeScript strict、明确的外部端口、SQLite 持久回执、身份与副作用边界测试、三平台 Node/SEA CI。不能因此认定所有模块都已足够优秀：若干核心文件接近 1000 行，职责混合与跨层依赖仍需逐步治理。

本次选择能够保持业务行为、便于验证的改动，不重写业务流程，不改持久格式，不顺带升级依赖：

| 问题 | 处理 | 保留的约束 |
| --- | --- | --- |
| 任务/编排模块从 app 导入共享记录、入口检查或回执核对 | 共享收件记录归入 core；编排契约和 Leader 回执核对归入 orchestration；任务入口检查归入 tasks | 字段、存储命名空间、检查顺序、错误码不变；旧导出路径保留兼容转发 |
| 报告投递依赖具体 Outbox 类 | 使用调用方拥有的最小 `ReportOutbox` 接口 | 仍由同一持久 Outbox 实现执行；不增加发送路径，不放松未知结果的禁止重放规则 |
| JSON 转义预算、Unicode 前缀、JSON 解析等相同逻辑多处复制 | 在 runtime 内共享真正同义的辅助函数 | 保持 JSON 转义后的 UTF-8 字节预算；不同的截断和省略号策略不强行合并 |
| lint 警告不阻断 CI，测试用 `!` 假定记录必然存在 | 显式检查记录存在，并启用 `--error-on-warnings` | 不关闭规则、不使用可选链绕过验证、不扩大超时来掩盖失败 |
| 模块边界只有约定，缺少回归约束 | `npm run check:boundaries` 纳入标准检查 | 同时检查静态导入、重导出、字面量动态导入、require 和 import 类型表达式 |

### 尚未解决的债务

- config 与 projects 之间的校验辅助模块归属，以及 herdr 与 transcripts 之间的屏幕文本清理依赖，仍可进一步整理。
- 任务与编排仍有双向协作；编排配置仍使用具体 `TaskService` 类型。本次消除的是它们对 app 的反向依赖，不声称整个模块图无环。
- Application、runtime engine/sessions、Leader 和 workflow runner 等大模块，需要按独立职责逐步拆分，并以现有行为测试保护；不为满足行数而机械分文件。
- 未做完整安全审计、性能基准、依赖漏洞扫描或新一轮真实飞书/模型验收。离线测试通过不代表这些项目已完成。

## 模块职责与依赖

| 模块 | 职责 | 约束 |
| --- | --- | --- |
| core | 共享领域记录、错误、标识和外部端口 | 本地依赖只指向 core |
| storage | 持久化、锁和操作回执 | 本地依赖只指向 storage/core |
| runtime | 模型会话、上下文预算、工具结果与恢复 | 本地依赖限于 runtime/core/config/storage |
| tasks | 任务与参与者生命周期、入口准入和原生输入 | 不导入 app/cli/web/feishu/onboarding；通过端口执行外部效果 |
| orchestration | 规划、决策、报告与 Leader 回执核对 | 不导入 app/cli/web/feishu/onboarding；跨层契约由消费者拥有 |
| app | 依赖组装、入口路由和交付协调 | 组合下层能力，不成为下层共享类型的唯一来源 |
| web/client | 浏览器展示和配置请求 | 运行时代码只引用 client 内部模块；共享 Web/core 类型必须 type-only |
| web/contracts | Web 与服务端之间的类型契约 | 只允许 type-only core 类型依赖，不能转发服务器实现 |

边界脚本解析 TypeScript AST，忽略注释与示例字符串，诊断包含路径和行号。服务端外部包、计算式 require（例如 SEA 原生模块加载）不属于本地层级解析范围；浏览器计算式导入则拒绝通过。它是当前明确边界的回归检查，不是通用依赖解析器或安全沙箱。若以后加入路径别名、包级拆分或新的模块加载机制，必须同步扩展检查与反例测试，不能添加大范围忽略项绕过边界。

## 复用与抽象原则

1. 先比较行为，再比较名称。只有输入、错误、空值、预算和副作用语义相同的逻辑才抽取；名字相同不等于职责相同。
2. 优先放在真正拥有该职责的模块；避免把所有工具函数塞入 core 或一个巨大的 utils。
3. 共享契约不依赖上层组装器。优先 type-only 导入；接口只暴露消费者确实需要的能力。
4. 不为一次调用构造通用框架。新增抽象须减少重复的业务知识，或明确隔离易变化的外部依赖。
5. 保留重要安全语义：用户身份来自可信入口；原生写入前再次检查目标；未知副作用不能自动重放；模型自述不能当作完成或送达证据。
6. 测试中的缺失记录用明确断言失败，不能靠 `!`、宽泛类型转换或可选链把真实问题推迟/隐藏。

## 开发与 PR 检查

使用 Node **24.13.0 或以上**，按锁文件安装：

```sh
npm ci
npm run check
npm run binary
npm run smoke
```

`npm run check` 按顺序执行源文件大小检查、模块边界检查、TypeScript、零警告 lint 和测试。需要局部验证时：

```sh
npm run check:boundaries
npm run typecheck
npm run lint
node --import tsx --test tests/build/module-boundaries.test.ts
```

- 当前上限为每个源文件 1000 行、单行 500 字符；它是防退化限制，不是设计优秀的证明。
- 使用 Biome 保持统一格式；只格式化本次改动文件，避免无关格式噪声。
- 并行开发需分配互不重叠的写入范围；最终全量验证必须在所有写入结束、代码稳定后运行，不能把移动模块过程中的测试结果当作最终结果。
- 回归测试优先临时目录、替身端口和固定输入，不读取生产密钥、不操作常驻服务。真实业务验收必须单独授权和记录。
- PR 说明应包括问题、范围、行为不变的证据、实际执行的命令、未验证项和剩余债务。最终 HEAD 的 CI 结果单独核对；不要用早先提交的绿色检查代替。
